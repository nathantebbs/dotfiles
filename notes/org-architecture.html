Org Mode architecture

2026-08-12dotfiles @ 99eddb1Design

The previous setup did not fail because it was badly designed. It failed because it was scaffolded around a semester, and the semester ended. Two mechanical faults made the collapse permanent rather than temporary: there was no capture, so adding an item cost more than most items were worth, and structure lived in deep heading hierarchies, so every add was a placement decision. This architecture fixes both by making capture unconditional and deferring all structure to a weekly review. Seven files, two keyword sequences, five capture templates, two agenda views, no new packages.

Historical design This document records the proposal that produced the current Org config. The work directory decision was resolved as ~/source/work-org. The config now lives in .emacs.d/configs/rc-org.el. See notes/org-guide.html for current usage.

What the old system actually got right

Worth stating, because the new design keeps these rather than reinventing them. The :@personal: / :@school: area tags were the correct instinct, just underused at two occurrences each. Repeating deadlines with a LOGBOOK drawer worked well for chores and ran for four consecutive weeks. CUSTOM_ID properties for cross-file linking were used 13 times and are the right mechanism. The dated session log in log.org accumulated nine real entries across two months, which makes it the single most-used habit in the whole system.

All four survive into the new design. The journal in particular gets promoted from a side file to a first-class capture template, because a habit that sustained itself under high friction will sustain itself better under low friction.

Why it stalled

No capture
There is no org-capture-templates anywhere in the config and no C-c c binding. Every item had to be filed by hand into the correct heading of the correct file. For a two-word errand that cost is higher than the errand.
Structure in hierarchy
Items lived at depth four (School > 460 Todo(s) > Exam #2 > Study for Exam #2). Depth means every capture is a navigation problem before it is a writing problem.
Undeclared keywords
projects.org used DEVELOPMENT, TESTING, and BACKLOG; assignments.org used SUBMITTED; the LOGBOOK drawers show a REVIEW state that no longer exists. None of these were in org-todo-keywords, so org rendered them as plain headline text and the agenda never saw them. You were tracking state the tool was blind to.
Semester-shaped
Course tags, an assignments file, and a per-course note tree. All of it became dead weight the moment you graduated, and dead weight in an active file is a reason not to open the file.

Two principles

Capture never requires a decision. The keystroke that records a thought must not ask where the thought goes. Anything that needs a decision lands in inbox.org and gets sorted in batch later. Anything that needs no decision goes straight to its home file. That single rule determines the whole template set.

Two axes of classification, one home each. The file says which area of life something belongs to. The tag says the context or sub-area. Nothing else carries classification meaning. The old setup had file, hierarchy, tag, priority, and keyword all encoding overlapping information, which is exactly the condition under which keywords drift out of sync with config.

Files

Seven files live across the two Org directories. The work file lives in ~/source/work-org. Each file answers one question. The questions do not overlap.

FileHoldsActionableCapture lands here
inbox.org Everything captured that still needs a decision. Never organized in place. triage Directly
life.org Personal tasks: chores with repeaters, admin, health, finance, errands. yes Via refile
work.org Job tasks. Empty until there is a job. yes Via refile
projects.org Personal projects, one subtree each, project status on the subtree root. yes Via refile
notes.org Reference material. Non-actionable by definition. no Directly, under * Unfiled
journal.org Dated record of what happened. Successor to log.org. no Directly, into a datetree
food.org Recipes and groceries. The concept worked; it returns empty. no Directly

The intended workflow uses life, work, and projects as the normal refile destinations. The implemented config offers every heading down to level three across all agenda files.

Keywords

Two sequences, both declared in config so they cannot drift the way the old set did. The letter in parentheses is the fast-select key; ! records a timestamp on entry and @ prompts for a note.

(setq org-todo-keywords
      '((sequence "TODO(t)" "NEXT(n)" "WAIT(w@/!)" "|" "DONE(d!)" "CANCELLED(c@)")
        (sequence "IDEA(i)" "ACTIVE(a)" "PAUSED(p@)" "|" "SHIPPED(s!)" "DROPPED(x@)")))

The first sequence is for tasks, the second for project subtree roots. The note prompt on WAIT is the important detail: "waiting on what?" is the question you will have about that item in a week, and if the answer is not recorded at the moment you set the state, it is gone.

Your old vocabulary maps onto this cleanly. BACKLOG becomes IDEA, DEVELOPMENT becomes ACTIVE, and SUBMITTED was school-specific and needs no successor. TESTING deliberately has no equivalent: it described a phase of one project, not the status of the project, so it belongs in a subtask.

Substitution to review You used IN-PROGRESS; this proposes NEXT. They are not synonyms. IN-PROGRESS means started, NEXT means this is the one thing I do next in this project. NEXT is what the day agenda filters on, which is why it is proposed, but it is your vocabulary and the substitution is trivial to reverse.

Tags

Declared in org-tag-alist, which gives completion and stops a typo from silently minting a new tag. Deliberately small.

(setq org-tag-alist
      '((:startgroup)
        ("@home" . ?h) ("@errand" . ?e) ("@computer" . ?c) ("@phone" . ?p)
        (:endgroup)
        ("health" . ?H) ("finance" . ?f) ("admin" . ?a) ("social" . ?s)))

The context group is mutually exclusive, which is what :startgroup: buys. Contexts answer "what can I do right now given where I am"; the second set are life areas for filtering. No effort estimates, no energy levels, no person tags, no someday tag. Someday is already expressible as IDEA.

Capture

Five templates on C-c c, one keystroke each. The split follows the first principle exactly: the top two need a decision and go to the inbox, the bottom three do not and go straight home.

A task capture writes a bare TODO with no scheduling prompt. Prompting for a date at capture time reintroduces exactly the friction this is meant to remove; the date is decided at review, when you can see the week.

Agenda

Two views. More views than you check daily is decoration.

C-c a d
Day. Today's scheduled and deadline items, then all NEXT items. This is the working view.
C-c a r
Review. Everything in inbox.org, then all WAIT items, then ACTIVE projects with no NEXT child. This is the view that keeps the system alive.

The review view is not optional infrastructure. An inbox without a scheduled review is a landfill, and the third block is what catches a project that has quietly stopped moving. That block is the single highest-value piece of the whole design, because a stalled project is invisible in every other view.

Resolved decision: where work.org lives

Resolved ~/source/org pushes to github:vetr0s/org. Work notes, ticket numbers, and internal names in a repo hosted outside the company is the kind of thing an employment agreement prohibits. This needs an answer before the first work item is captured, because moving it afterward means rewriting git history rather than moving a file.

The config uses a second, local-only repo at ~/source/work-org holding work.org. org-agenda-files is a list, so a second directory entry costs nothing and both files appear in one agenda.

The alternative of gitignoring work.org inside the existing repo is worse than it looks. It silently stops being backed up, and you will not notice until you need it.

Implemented config

All of this is built-in org. No new packages, so pre-init.el is untouched and the deliberate absence of ELPA org stays intact. Everything lands in .emacs.d/configs/rc-org.el. It implements the full workflow described below.

  • org-directory, and org-agenda-files as two directory entries.
  • org-capture-templates plus a C-c c binding.
  • org-refile-targets across every agenda file through level three.
  • org-todo-keywords, two sequences, and faces extended to match.
  • org-log-done and org-log-into-drawer.
  • org-archive-location pointing inside archive/.
  • org-tag-alist.
  • org-agenda-custom-commands, two views.

The existing keyword faces inherit from theme faces rather than naming colours, which is correct and worth preserving as the sequences grow: it keeps the keywords following modus-themes-toggle.

Deliberately not included

Named so that leaving them out reads as a decision rather than an oversight. org-roam and denote: you stalled on friction, and a second organising system is more friction, not less. Revisit only if notes.org genuinely outgrows a single file. org-super-agenda: two views do not need grouping. Effort estimates and clocking: real value, but only once the capture-and-review loop is a habit. Mobile sync: it was on the old project list and never got done; it is a separate project, not part of this one.

Original phasing

  • Archive the prior contents. All seven paths moved under archive/ as git renames, history preserved, nothing committed.
  • Write rc-org.el and create the seven files with headers only.
  • Use it for two weeks and change nothing. Resist tuning; the point is finding out which parts you actually touch.
  • Then, and only then, revisit the excluded list above.
Verified org-agenda-files set to a directory expands non-recursively. Tested against a scratch tree: a root-level root.org is found, a nested sub/nested.org is not. So archive/ stays out of the agenda with no exclusion rule, and the same holds for org-archive-location targets placed inside it.
